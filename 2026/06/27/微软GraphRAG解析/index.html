微软GraphRAG工作原理解析

https://zhuanlan.zhihu.com/p/1922782829256868561

阶段一：数据索引与图构建（Indexing Pipeline）

这是 GraphRAG 最耗时、成本最高，但也是最核心的阶段。它通过 4 个步骤将非结构化文本变成“结构化大脑”：

1. 文本切片与文本单位（Text Chunks → Text Units）

  • 做法： 输入的大型文档（如一本书或数千份报告）被切分成固定大小的文本块（Chunks），在源码中被称为 TextUnit（默认通常为 600 个 Token）。
  • 目的： 确保每块文本大小适中，既包含足够的上下文，又不会因为太长而让 LLM 在后续抽取时丢失细节。

2. 元素抽取（Element Extraction：实体与关系）

  • 做法： 利用 Prompt 引导 LLM 仔细阅读每个 TextUnit，提取出所有的实体（Entities）、关系（Relationships）和声明（Claims，如某人某时发表的言论）。
  • 图的雏形：
    • 节点（Nodes）： 实体（如：张三、微软公司、AI技术）。
    • 边（Edges）： 关系（如：张三 -> 服务于 -> 微软公司）。
    • 权重（Weight）： 如果多个文本块都提到了同一个关系，边的权重就会增加。

claims
Claims（声明/断言） 并不是指实体的属性（Attributes），而是一个独立的、带有时间线和上下文的事实动态记录。

微软 GraphRAG 中的 Claims 数据结构

在微软的论文和源码中，Claims 通常被定义为 Covariates（协变量） 的一种主要类型。一个标准的 Claim 在被 LLM 提取出来时，通常包含以下结构化的字段：

  • Subject（主体）： 该断言的核心实体。
  • Type（类型）： 通常是特定的行为、状态或事件类型（例如：threat 威胁、fraud 诈骗、achievement 成就）。
  • Description（详细描述）： 这个断言具体说了什么（比如：“张三在2025年被指控泄露了公司的核心商业机密”）。
  • Status（状态）： 该断言目前的状态（如：true 已证实、suspected 嫌疑、denied 否认）。
  • Start/End Date（时间戳）： 事件发生的起始和结束时间。
  • Source Text（出处）： 这句话是从哪一个 TextUnit（文本块）里读出来的。

假设原始文本里有这样一句话：

“2024年3月，李四在公开会议上指责王五的公司存在严重的财务造假行为，但王五对此予以坚决否认。”

如果只提取实体和关系（传统的图 RAG），你可能会得到：

  • 实体： 李四、王五的公司
  • 关系： 李四 --[指责]--> 王五的公司

但如果开启了 Claims 提取，LLM 会额外生成两个 Claims（断言记录）：

字段 Claim 1 (李四的指责) Claim 2 (王五的否认)
Subject (主体) 王五的公司 王五的公司
Type (类型) FINANCIAL_FRAUD (财务造假) FINANCIAL_FRAUD (财务造假)
Description 李四在公开会议上声称该公司存在严重财务造假。 王五坚决否认公司存在财务造假行为。
Status (状态) SUSPECTED (嫌疑/声称) DENIED (否认)
Date (时间) 2024-03 2024-03

为什么要单独提取 Claims？

微软 GraphRAG 引入 Claims 主要是为了解决**知识的“时效性”和“冲突性”**问题：

  1. 处理矛盾与多方观点： 在现实世界的文本中，不同的人对同一件事有不同的说法（比如李四说有造假，王五说没有）。Claims 能够把这些相互冲突的断言同时保留下来，而不是粗暴地合并成一条错误的关系。
  2. 增强时间线推理： 当用户询问“某事件的发展脉络是什么？”时，系统可以绕过复杂的拓扑网络，直接筛选出与该实体相关的所有 Claims，并按时间戳（Start/End Date）排序，瞬间拉出一条清晰的事件发展时间线。

3. 实体消歧与图合并（Entity Resolution）

  • 做法： 文本中可能会出现“文本 A 提到‘微软’，文本 B 提到‘Microsoft’”，LLM 会自动识别它们指向同一实体，并在图谱中将这两个节点合并，把它们的描述（Descriptions）连接在一起。

4. 社区检测与分层摘要（Community Detection & Summarization）—— 微软的核心创新

这是微软 GraphRAG 区别于其他图 RAG 的关键：

  • Leiden 算法聚类： 系统使用 Leiden 算法（一种无监督的图聚类算法），根据网络拓扑结构，把联系紧密的实体强行聚合成一个一个的**“社区（Communities）”**。
  • 分层架构： 聚类是分层的。高层级（Level 0）可能把整个图划分成 3 个巨大的宏观社区；中层级（Level 1）细化为 15 个社区；底层级（Level 2）细化为上百个微观小社区。
  • LLM 生成社区摘要（Community Reports）： * 对于每一个社区，系统都会把该社区内所有的实体和边打包，丢给 LLM。
    • LLM 会为这个社区写一份极其详细的报告（包含核心主题、涉及实体、潜在风险/关联）。
    • 意义：这些报告取代了原始文本，成为了后续“全局查询”的检索基础。

阶段二：查询与生成阶段（Querying Engine）

当用户提出问题时，微软 GraphRAG 提供了两种完全不同的数据流动路径（Query Modes）：

Mode 1: 全局查询（Global Search）—— 处理宏观/总结性问题

适用于宽泛、总结性的主题，例如：“微软公司的发展历史”、“AI技术的最新趋势”。

  • 社区加权与分批：系统首先计算每个社区的出现权重（occurrence_weight），该权重反映了社区相关实体在整个文档中的普遍程度。然后，所有社区被打乱顺序并分成多个批次（batch），以减少偏差，这里分批操作会参考occurrence_weight，保证每个批次的社区数量与平均重要性大致相同。
  • 多路中间件生成（Map 阶段）：对于每个社区批次，LLM会以该批次的社区报告为上下文，生成多个对用户问题的回答，并为每个回答打分（0-10分），以评估其相关性。
  • 汇总与过滤：系统过滤掉评分低、不相关的中间解答，把高分解答按重要性排序。
  • 生成最终答案（Reduce 阶段）：后，系统将所有高质量的中间回答文本拼接成一个新的上下文，再次提交给LLM，要求其基于这些信息生成一个全面、连贯的最终答案。

Mode 2: 局部查询（Local Search）—— 处理微观/多跳推理问题

  • 检索相关实体：系统根据用户问题，从图谱中检索出所有与该问题相关的实体。
  • 构建候选集：这N个实体被称为候选实体。系统会围绕这些实体进行扩展，构建出四个候选集。
    • 候选社区：所有包含至少一个候选实体的社区。
    • 候选关系：所有以候选实体为源节点或目标节点的边。
    • 候选文本单元：所有包含至少一个候选实体的原始文本块。
  • 上下文重组：系统会将所有候选实体、候选关系、候选文本单元，经过排序和筛选之后重新组织成一个新的上下文。
  • 生成最终答案：系统会以这个新的上下文为上下文，再次提交给LLM，要求其基于这些信息生成一个全面、连贯的最终答案。
