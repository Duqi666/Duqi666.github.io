GraphRAG

一、核心模式

1、混合检索与双路召回（Hybrid Retrieval）

通过用户的输入做两步查询并融合

  • 文本向量路（Dense Retrieval）： 计算用户问题与原始文本 Chunk 的 Embedding 相似度，捞出相关的上下文。

  • 图谱实体路（Graph Retrieval）：

    1. 提取问题中的核心实体（如上一节提到的 LLM 或小模型 NER）。
    2. 去图数据库（如 Neo4j、NebulaGraph）中，捞取该实体周围 1跳（1-hop）或 2跳（2-hop） 的所有三元组（如属性和邻居节点）。
  • 重排融合（Reranking）： 使用 混合交叉编码器（Cross-Encoder Reranking） 或 RRF（倒数排名融合），把向量块和三元组拼在一起重新打分，挑出含金量最高的 Top-K 内容喂给 LLM。

2、Text-to-Cypher / Text-to-SubGraph（大模型生成查询）

当面临复杂的多跳逻辑推理（例如：“提取出所有由李彦宏投资、且总部在上海的医疗健康领域公司的名字”）时，直接靠向量匹配会彻底失效。目前的主流是让 LLM 充当翻译官。

  • 做法： 系统把图谱的 Schema（本体结构定义：有哪些节点标签、哪些关系类型） 作为 Context 喂给大模型，让大模型直接将用户的自然语言问题，“翻译”成图数据库的专用查询语言（如 Neo4j 的 Cypher 语句，或 RDF 的 SPARQL）。
  • 执行： 后端服务直接执行这条 Cypher 语句，从图数据库中极其精准、无噪声地“抠出”对应的子图数据。

3、Agentic GraphRAG（智能体自主探路）

2026年，业界正在大量转向 Agentic（智能体化） 的提取方案。因为传统的固定多跳（固定查两圈）要么带入太多噪声，要么漏掉关键信息。

做法： 把图谱检索做成大模型的一个 Tool（工具调用，Function Calling）。大模型化身为一个 Agent，它可以自主决定如何探索这张图：

  • 第一步： 看到问题后，Agent 先调用工具：search_entity(“李彦宏”)。
  • 第二步： 拿到李彦宏的 1 跳关系后，Agent 发现里面有一个关键节点“小度音箱”，它会自主进行第二轮思考，再次调用工具：explore_relations(“小度音箱”, “芯片供应商”)。
  • 第三步： 像人类探案一样，沿着图谱的边自主肉眼可见地一步步探索（Walk），直到它认为拿到了足够回答问题的证据，才停止检索。

4、全局归纳神器：基于社区报告的宏观检索（Community-based Retrieval）

如果用户的问题非常宏观，比如：“这份技术文档里提到的无线信道建模方法，目前主要的性能瓶颈都在哪里？”，此时图谱里没有任何一个单一实体能对应这个问题。

  • 做法（微软 GraphRAG 的核心精髓）： 在构建期，利用图算法（如 Leiden 算法）已经把整张大图划分成了无数个“社区”，并用 LLM 提前为每个社区生成了“社区摘要报告（Community Reports）”。
  • 提取时： 计算用户问题与这些社区报告的向量相似度，直接捞出最相关的几个“宏观社区报告”，让大模型直接阅读这些高级摘要来回答问题。这直接跳过了去捞具体三元组的步骤。

5、工业落地

在实际的企业级项目中，通常会部署一个 动态路由（Adaptive Routing） 机制：

  • 用户提问 ──> 先经过一个轻量级分类器（或小 LLM）。

  • 如果是具体/事实性问题（如“某型号设备的功耗是多少”），走 混合检索（向量 + 实体1跳召回）。

  • 如果是多维/关系交织问题（如“找出所有和A供应商有业务往来且评级为B的子公司”），走 Text-to-Cypher 路由。

  • 如果是宏观/总结性问题（如“整篇文档的核心要点是什么”），走 GraphRAG 社区报告检索。

二、实体消歧

在大规模文本提取时，同一个实体可能会有不同的写法（如 “Apple”, “Apple Inc.”, “苹果公司”）

所有的消歧的方法的逻辑基本上都是分成两个部分：

  • 粗筛：先用一些比较快速的方法将可能相同的实体筛选出来；
  • LLM裁判：将粗筛出的实体送入 LLM，让 LLM 来判断哪些是同一个实体，哪些是不同的实体。

1、实体提取即时消歧

在实体抽取阶段就可“顺带”消歧。

  • 机制： 给 LLM 的 Prompt 中包含了严格的格式化约束。当 LLM 在阅读同一个 TextUnit 时，Prompt 会要求它：“如果发现同一个实体有不同的称呼，请在输出时统一使用其官方名或最常见的名字，并将其他别名放入描述（Description）中。”
  • 局限： 这种方式只能解决同一个文本块内部的消歧，无法跨文本块处理。且并不能完全解决一个文本块中的实体消歧问题，因为 LLM 无法判断实体的业务属性（如实体类型、属性值等），只能根据文本内容来判断。

2、粗筛

2.1 分桶

不管使用说明粗筛方法，都无法避免两两实体的对比，但是当实体很多时，这样的计算量无法解释，所以需要对实体就行分桶

1、确定性分桶

  • 前缀/首字母分桶（Prefix Blocking）： 比如按英文首字母、中文拼音首字母，或者机构名的前两个字分桶。
  • 属性聚合分桶（Attribute Blocking）： 结合实体的业务属性。例如实体类型是“人名”，且“出生年份=1963”或“国家=中国”。只有当这些硬性标签一致时，才把它们分到一个组里进行下一步的相似度比对。

2、基于局部敏感哈希（LSH, Locality Sensitive Hashing）的模糊分桶

3、向量空间的分区检索（ANN 索引分块）

4、依托拓扑结构的社区划分（Graph Partitioning —— GraphRAG 核心）
GraphRAG 最经典的“分组”方式就是社区发现（Community Detection）。

  • Leiden / Louvain 算法： 这些算法在纯图拓扑结构上运行，根据边的紧密程度（模块度 Modularity）将大图切分成一个个互不重叠的社区（Communities）。
  • 组内消歧： 图谱构建系统会规定：只有属于同一个 Leiden 社区内的实体，才具备相互消歧的资格。 跨社区的实体直接免检。这不仅避免了 $O(N^2)$ 计算，还天然自带了上下文隔离（比如“苹果”在水果社区和在科技公司社区，由于不属于同一个社团，压根不会放在一起比对）。

2.2 组内粗筛

  • 传统字面相似度匹配，可能使用N-Gram 相似度等方法，直接判断实体本身；
  • 将实体或相关描述转化embedding，然后对比余弦相似度
  • 依据图结构，如果某个实体的邻居和关系高度相似则认为可能是相同实体

3、LLM裁判

把粗筛出来的“疑似重复实体对”（比如 (实体A, 实体B)）喂给 LLM。这时候会把它们的上下文、属性列表、一阶邻居关系全部打包成 Prompt 塞给大模型，让大模型做逻辑推理：

“根据以下背景，请判断 A 和 B 是不是同一个东西？如果是，请给出一个融合后的新名字和新描述。”

4、外置消歧器

在工程上，大部分时间还是采用外置消歧的方法，例如人为设置一个json，规定“apple”:[“apple”,”apple.inc”,”苹果公司”]，直接使用人为设置去做消歧
